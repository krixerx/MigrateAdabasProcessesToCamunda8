## Problem Statement

A government registry runs "Apply for a learner permit" on IBM mainframe Adabas. There is no workflow engine: process state is implicit in combinations of field values on an Adabas file (`issued`, `expired`, `date_completed`, `fee_paid`, `visual_test`, `user_id`, `user_name`). The replacement system is Camunda 8 with an executable BPMN process.

The migration must move **in-flight** applications, not just reference data. Because state was never recorded explicitly, the migration has to **infer** where each case sits in a process that was never written down, from data alone, and place a token there.

This POC proves that inference can be done **correctly**, with every exception accounted for, and **measures** what happens at volume. It does not claim production readiness.

## Demand Evidence

- Committed migration programme with a cutover date. Not exploratory.
- Hard cutover is mandated. Verbatim: *"we have 2 systems: old Adabas and new based on Camunda 8. When we switch using to new system, everything should be switch to new. We can't allow situation where some users are still using old system with old database and some new system with new database, this will cause a real mass."*
- Scale: thousands of active processes.
- A working sibling system already exists: Camunda 8.9.12, Keycloak, a real learner-permit BPMN, DMN and forms in production layout.

## Status Quo

The standard fallback is drain-the-queue: freeze intake early, dual-run, let the old system empty, switch it off. **Explicitly ruled out**, for a sound reason: a citizen permit record existing in two systems with divergent truth means no clerk can tell which is authoritative, and the answer a citizen gets depends on which channel they walk into.

Ruling out dual-run removes the safety net. It makes in-flight migration mandatory and makes this POC the programme's critical path.

## Target User & Narrowest Wedge

> **Correctness plus quarantine.** Every in-flight record either lands at the right task, or is detected and quarantined before the cutover window closes. 100%, or a known and listed exception set. In a hard cutover there is no "we'll catch the rest later."

**Users of the migrated output:** three **back-office** roles.

| POC element id | Candidate group | Role |
|---|---|---|
| `vision-assessment` | `civil-servant` | Assessment reviewer |
| `cashier-fee-review` | `cashier` | Cashier confirming counter payment |
| `issuing-review` | `issuing-officer` | Issuing officer |

**Citizen-facing tasks are out of migration scope, deliberately.** Verified in the sibling model: its citizen-facing tasks carry an individual `assignee` expression resolving to the applicant's own id, while candidate-group assignment is used only for back-office work. Assignment is evaluated at task creation, and the sibling's case-access layer matches that applicant id against the Keycloak `preferred_username` — so a migrated citizen task assigned to the legacy string `K.TAMM` would be unreachable, locking the applicant out of their own application.

Any record classifying to a citizen-facing element is quarantined with reason `CITIZEN_TARGET`. **This is a guard against rule-set growth, not a reachable path today** — R5 to R7 all target back-office elements, so its expected count in the fixture run is zero. It exists so that a future rule added without reading this section fails loudly instead of locking a citizen out.

| Constraint | Consequence |
|---|---|

## Cross-Model Perspective

Independent cold read by Codex (gpt-6-astra, high reasoning), which had not seen the conversation:

### Prior art: Camunda's own runtime migration

The loader follows Camunda's documented Camunda 7 → 8 **runtime** migration procedure, not a mechanism of our own. Two things carry over and one does not.

**Carries over — the mechanism.** Halt at the start event via a `migrator` execution listener, create with a `legacyId`, position the token, verify, then remove the listeners and redeploy. Temporary model changes are an explicit, documented part of Camunda's own procedure, which settles the question of whether a migration-only BPMN element is acceptable: the vendor does it too.

**Carries over — the state model, independently arrived at.** The official tool records skipped instances in a **migration database** with `--list-skipped`, `--retry-skipped` and `--list-migrated`. That is our ledger and our quarantine queue. Its skip taxonomy (no matching target definition, active multi-instance activity, a flow node absent from the deployed model) maps onto our reason codes. Two designs reaching the same shape from the same constraints is corroboration worth stating.

**Does not carry over — the source half, which is the hard half.**

```
Camunda 7 → explicit active task + variables      → Camunda 8
Adabas    → business fields → INFER AND VALIDATE  → Camunda 8
```

Camunda 7 already knows where each instance waits. The Data Migrator reads that from a C7 database. **We have no C7 database and no recorded position** — the entire premise is that Adabas has no engine. Extract, pre-validation, DMN classification, the distinct-output branching, the freeze manifest and the reconciliation identity are ours and are unaffected by adopting the official loader. The official tooling replaces roughly the last 20% of the pipeline and none of the risk.

Also not applicable: the C7 code and integration conversion tooling. There are no C7 delegates or job handlers here; the Camunda 8 side (the sibling POC) is already native.

- **A: Classifier-First Rehearsal.** Frozen fixtures, no Adabas. Effort S. **Rejected as the whole answer** — never exercises PE/MU flattening. Its sequencing survives as iteration 1.
- **B: Full Cutover Rehearsal.** Real Adabas CE, Postgres ledger, quarantine as a BPMN process. Effort L. **Chosen architecture.**

## Recommended Approach

**Approach B's architecture, CSV source in iteration 1, Adabas CE optional in iteration 2.**

### Why CSV first

An Adabas export is not tidy JSON. A PE group of vision-test attempts and an MU field of restriction codes export as repeating occurrences:

```csv
CASE_REF,ISN,USER_ID,USER_NAME,LAST_UPDATED,FEE_PAID,VT_1_DATE,VT_1_RESULT,VT_2_DATE,VT_2_RESULT,RESTR_1,RESTR_2,ISSUED,EXPIRED,DATE_COMPLETED
LP-2026-004711,8891,K.TAMM,Kadri Tamm,2026-04-11,TRUE,2026-03-02,FAIL,2026-04-11,PASS,,,,,
LP-2026-004712,8892,M.SAAR,Mihkel Saar,2026-05-20,FALSE,2026-05-20,FAIL,,,B,,,,
LP-2021-004713,8893,A.LEPP,Anu Lepp,2021-03-04,TRUE,,,,,,,2021-03-04,2024-03-04,
```

Record 004711 has two PE vision-test occurrences; 004712 has one MU restriction code. The decision table needs one `visionOutcome` value. **Something must decide: latest occurrence, first PASS, or attempt count?** That collapsing rule is contested business logic, invisible if fixtures are hand-written clean.

**`LAST_UPDATED` is an addition to the original field list.** The 6-month cutoff cannot be evaluated without a date carrying case age, and `VT_1_DATE` is no substitute (a case with no vision-test attempt has no date). Identifying the real field is a prerequisite (OQ10).

### Identifiers

| Name | Definition |
|---|---|
| `legacyId` | **`CASE_REF`, a durable business key.** NOT the ISN. A **design choice of the invented model**, not a discovery about the real file. |
| `ISN` | Carried as audit metadata only. An Adabas ISN is a physical record address that changes across ADAULD/ADALOD and file reorganisation, so it is unsafe as a ledger key, a manifest identity, or a dedup key. |
| `runId` | UUID per migration run. Scopes the ledger key. |

**Carried forward to the programme, not resolved here:** the POC assumes a durable business key exists because it invents one. Whether the real file has one is a genuine open risk — if it does not, the ledger key, manifest identity and duplicate detection all need redesigning. The POC cannot answer this and does not claim to.

### Key derivation (2026-09-15)

**The process key is derived deterministically from the initial Adabas record.** Same record, same key, every run, forever.

This is the intended route to cross-run idempotency, and it is stronger than a database guard: duplication stops being something you prevent and becomes something that cannot occur by construction — provided the key is also enforced as unique, either by the engine (probe M8, `businessId` uniqueness) or by a ledger key that does **not** include `runId`.

**Hard requirement: it must be a business key, not the ISN.** An Adabas ISN is a physical record address that changes across `ADAULD`/`ADALOD` and file reorganisation. A reorg between freeze and load would silently re-identify every record. The POC invents `CASE_REF` for this purpose; confirming the real file carries an equivalent is OQ10 and remains open.

### Key design decisions

**Classification: DMN `COLLECT`, no catch-all row, branch on distinct outputs.**
1 distinct = proceed; 2+ identical = proceed and increment `REDUNDANT_RULE`; 2+ distinct = `QUARANTINE_AMBIGUOUS`; 0 = `QUARANTINE_UNMATCHED`. Branching on raw hit count would quarantine harmlessly redundant rules and inflate the exception queue on the one night it must be small.

A catch-all row is forbidden: under `UNIQUE` it overlaps everything; under `FIRST` it hides rule conflicts behind row order.

**Read `evaluatedDecisions[].matchedRules[]`, never the top-level output.** Verified against the sibling COLLECT table: a non-matching evaluation returns top-level `"output": "null"` — the *string* — with `matchedRules: []`. Branching on the top-level value would treat "no match" as a value. `matchedRules[]` carries `ruleId` and `evaluatedOutputs[].outputValue`, which is what the 0 / 1-distinct / 2+-identical / 2+-distinct branching needs. The sibling POC's own BPMN carries a comment about this same FEEL trap (`count(null)` is null, not 0).

**What this does and does not give you.** It gives **unmatched detection** and **overlap detection**, per record. It does **not** give exhaustiveness — that is a property of the rule set over the input domain, and DMN will not check it. Exhaustiveness is a separate build-time check (criteria 9a, 9b).

> **Note on the sibling DMN.** The sibling's eligibility table also uses `COLLECT` with no catch-all, but **the semantics are inverted**: there, an empty result means *eligible* (the happy path) and multiple hits are normal and desired. Here, empty means failure. Only the XML attribute carries over. Do not "align" these two tables.

**Null policy: there are no nulls.** extract normalises every DMN input to a total value. In FEEL an input entry tested against a null input generally does not match, so a null-carrying record would fall to zero hits and quarantine *whether or not that was intended* — the unmatched count would then measure FEEL semantics rather than rule coverage.

**Pre-validation** runs in extract, before the DMN, and quarantines with reason `PREVALIDATION`:

| Check | Rationale |
|---|---|
| `legacyId` (`CASE_REF`) missing or non-unique | Ledger key, manifest identity and dedup key all depend on it |
| `USER_ID` missing | Starter identity unrecoverable |
| `LAST_UPDATED` missing or unparseable | **Must not default.** A missing date would normalise to `withinCutoff=false` → R4 → skipped, silently dropping a live case |
| PE occurrence count exceeds discovered columns | Truncation is data loss, never silent |
| `expired ∧ ¬issued` | A permit that expired without being issued |
| `dateCompleted ∧ ¬issued` | Completed without issuance |

The contradiction set is explicit and testable. It reduces the DMN's effective input domain, which is why R4-R8 can leave `hasExpired` unconstrained.

**Hold on arrival: Camunda's own runtime-migration mechanism.**

This follows the documented Camunda 7 → 8 runtime migration procedure rather than a mechanism of our own. ([Runtime migration docs](https://docs.camunda.io/docs/guides/migrating-from-camunda-7/migration-tooling/data-migrator/runtime/))

1. **Hold.** The process-level None Start Event carries a `migrator` execution listener, which "ensures the process instance execution waits for the Data Migrator at the start event":

   ```xml
   <bpmn:startEvent id="apply-for-permit">
     <bpmn:extensionElements>
       <zeebe:executionListeners>
         <zeebe:executionListener eventType="end" type="migrator" />
       </zeebe:executionListeners>
     </bpmn:extensionElements>
   </bpmn:startEvent>
   ```

2. **Create.** load creates an ordinary instance carrying `legacyId` and `runId`. It halts at the start event **before traversing any sequence flow**, so no service task can fire. Stronger than a router, where the token traverses a flow to reach its target.
3. **Position.** The held job is completed via `POST /v2/process-instances/{key}/modification` — `activateInstructions` for `targetElementId` (with scoped `variableInstructions`) plus `terminateInstructions` for the start-event token. **Probed and accepted on 8.9.12** (see Verified facts). The docs describe create → halt → activate-job and stop; the positioning step is not documented, so **probe M1 gates this**.
4. **Release is ONE operation: the `modification` call.** Success is defined as *the target element is active*. Activating the target is what makes the case live — completing the held migrator job afterwards is not a second barrier, and the job may not survive termination of its own start-event token (probe M7). Treating it as two steps would leave a failure class that cannot be distinguished from success: the case is already live and the ledger says `RELEASE_PENDING`, which the abort path would then treat as safely held. No message, no correlation key, no TTL.

   **Activation is explicit, never a polling worker.** `reconcile` activates migrator jobs only after the gate passes. A Spring `@JobWorker(type = "migrator")` polls continuously and would complete held jobs the instant they appear, releasing every case before the gate runs — the hold would look implemented and **fail open**. Camunda's own migrator activates listener jobs explicitly and filters on `legacyId` for the same reason.
5. **Cleanup, an explicit documented phase:** *"Remove `migrator` execution listeners from Camunda 8 models"*, *"Revert temporary model changes"*, *"Redeploy the updated models."*

**Why this over the message-start / hold / router mechanism it replaces:** the BPMN delta shrinks from a permanent gateway with N outgoing flows to one listener attribute that is deleted at cleanup; any element is a valid target without modelling a flow to it; and it removes both the `timeToLive` tuning problem and the run-scoped correlation-key collision outright. `startInstructions` remains verified and viable as a second fallback.

**Coexistence.** The docs are emphatic: *"Do not start new Camunda 8 process instances on models that still have the `migrator` execution listener"* — an instance started without `legacyId` halts at the start event (documented as harmless, but stuck). **A hard cutover makes this free:** the migration window is by definition a period when nothing new starts. Migrate → gate → release → remove listeners → redeploy → open the service. The documented escape hatch (`validation-job-type` = `=if legacyId != null then "migrator" else "noop"` plus a `noop` worker that completes immediately) is carried as a **safety net** against an accidental start during the window, not as a dependency.

**Cost of the swap, stated plainly: idempotency returns to the ledger.** Message-start dedup was chosen partly to avoid an eventually-consistent `legacyId` lookup. Without it, a retried create can produce a duplicate instance. Three things make that acceptable, and it is how Camunda's own migrator behaves too (it tracks state in a migration database, not via engine dedup):

- A duplicate is **inert**: it is held at the start event, has fired nothing, and is citizen-invisible.
- A duplicate is **detectable before release**: the gate requires **exactly one non-`ABORTED` instance per `(runId, legacyId)`**, queried by variable. A violation blocks release.
- A duplicate is **cancellable** with no effect, by the same path as abort.

This is strictly safer than the failure it replaces, because the old risk was a duplicate that had already proceeded.

**Safety invariant, enforced by a build-time check on the BPMN:** every declared `targetElementId` must be a valid modification target — not inside a multi-instance activity, not inside an event subprocess, and present in the deployed model. These mirror the documented skip reasons (active multi-instance activities; a flow node absent from the deployed model). Verified benign in the sibling model today (three exclusive gateways, no subprocesses, no boundary events), but the POC authors new elements.

**Abort.** Instances are held and no side effects have fired, so cancellation is safe. A failed gate drives cancellation of every `CREATED`/`RELEASE_PENDING` instance, marks them `ABORTED`, and the next run uses a **new `runId`** — which is what makes rerun possible despite both idempotency guards. **Invariant: a held instance is cancellable with no citizen-visible effect**, defined operationally as criterion 8.

**Ledger** (Postgres 17). Key `(runId, legacyId)` unique.

| From | To | Trigger | Writer |
|---|---|---|---|
| — | `EXTRACTED` | record read, hash matched manifest | extract |
| `EXTRACTED` | `QUARANTINED` | pre-validation failure | extract |
| `EXTRACTED` | `CLASSIFIED` | DMN returns 1 distinct output | classify |
| `EXTRACTED` | `QUARANTINED` | 0 hits, or 2+ distinct outputs | classify |
| `CLASSIFIED` | `SKIPPED` | outcome = SKIP | classify |
| `CLASSIFIED` | `QUARANTINED` | outcome = QUARANTINE (e.g. R4 `OUT_OF_CUTOFF`) | classify |
| `CLASSIFIED` | `QUARANTINED` | per-target variable contract unsatisfied (`CONTRACT_UNSATISFIED`) | classify |
| `CLASSIFIED` | `CREATE_PENDING` | intent written, before API call | load |
| `CREATE_PENDING` | `CREATED` | create confirmed | load |
| `CREATE_PENDING` | `CREATE_FAILED` | definitive engine rejection | load |
| `CREATE_PENDING` | `PENDING_RESOLVED_EXISTS` / `_ABSENT` | operator decision after re-check window | operator |
| `PENDING_RESOLVED_EXISTS` | `CREATED` | instance confirmed present | operator |
| `PENDING_RESOLVED_ABSENT` | `CREATE_PENDING` | retry creation | load |
| `CREATE_FAILED` | `QUARANTINED` | routed to triage, reason `CREATE_FAILED` | reconcile |
| `CREATED` | `RELEASE_PENDING` | gate passed, release intent written before the modification call | reconcile |
| `RELEASE_PENDING` | `RELEASED` | **`modification` applied and the target element confirmed active.** That is the whole release. | reconcile |
| `RELEASE_PENDING` | `RELEASE_FAILED` | modification rejected or unconfirmed | reconcile |
| `RELEASE_FAILED` | `RELEASE_PENDING` | retry after operator review | reconcile |
| `CREATED` / `RELEASE_PENDING` | `ABORTED` | gate failed, instance cancelled | reconcile |
| `QUARANTINED` | `CREATE_PENDING` or `SKIPPED` | quarantine process resolution | quarantine worker |

**State → reconciliation bucket** (so the identity is checkable by construction):

| Bucket | States |
|---|---|
| `migrated` | `CREATED`, `RELEASED` |
| `skipped` | `SKIPPED` |
| `quarantined` | `QUARANTINED` |
| `pending` | `EXTRACTED`, `CLASSIFIED`, `CREATE_PENDING`, `PENDING_RESOLVED_*`, **`RELEASE_PENDING`** |
| `failed` | `CREATE_FAILED`, **`RELEASE_FAILED`** |
| `aborted` | `ABORTED` |

Idempotency is enforced by the unique constraint, not application logic. Parallel workers claim rows with `SELECT … FOR UPDATE SKIP LOCKED`. **Honest scope note:** iteration 1 runs single-worker; the concurrency design exists so the cutover-window story needs no rewrite, and is exercised only by the volume run (criterion 11).

**Quarantine has an exit.** `quarantine-case.bpmn`: human task (candidate group `migration-triage`) carrying **`runId`**, `legacyId`, source hash, reason code and matched rule ids — `runId` is required because the ledger key is `(runId, legacyId)` and the worker must write it → outcome gateway: (a) **resolve to a target** — operator chooses `targetElementId`, which calls the same intent→create→confirm path; (b) **no migration required** — terminal, ledger `SKIPPED`. **Both branches write the ledger**, or resolving quarantine silently breaks the reconciliation identity.

**Data minimisation.** Migrated and quarantine instances carry **identifiers (`runId`, `legacyId`), the per-target variable contract, and the source hash** — not the full record, which stays in the ledger. Zeebe variables export to the secondary store, which would otherwise place citizen personal data in a new searchable store with its own retention and erasure obligations, in a programme whose security posture bars production data from the POC entirely. Retention and erasure is OQ8, owner required.

**Per-target variable contract.** A token landing at a target must be able to flow onward. Each target declares the variables its downstream elements require, derived from the BPMN.

**This check runs post-classify, pre-load — not in pre-validation.** The contract is per target, and `targetElementId` is a DMN *output*, so it does not exist when extract runs. A record whose contract cannot be satisfied is quarantined with reason `CONTRACT_UNSATISFIED`. A case that lands correctly and then raises an incident on the next element is not migrated correctly — criterion 5 tests the success branch, fixture 12 the failure branch.

**Freeze and control total.** The freeze step emits a **manifest** with a header (`freezeDate`, `cutoffMonths`, `runId`, record count) and one row per record (`legacyId`, hash). The hash input is the **raw, byte-exact source line**, canonicalised only by stripping a trailing CR — deliberately not the normalised record, so a change to normalisation does not invalidate every manifest. extract reads `freezeDate` from the manifest, **never from the clock**, so reruns on a later day cannot reclassify. A changed hash means the source was not frozen: the run halts.

**Language and packaging: one Spring Boot application, four entry points** (`extract`, `classify --dry-run`, `load`, `reconcile`). Four separate services would be mechanism, which P1 deprioritises.

## Success Criteria

1. Dry run creates **no process instances and no user tasks**. Decision-evaluation records in Operate are expected and are the dry run's audit trail.
2. All 13 fixture records match their hand-written expected outcome (outcome, target element, reason code): 13/13. Plus two overlap-variant unit tests for `AMBIGUOUS` and `REDUNDANT_RULE`.
3. Reconciliation balances against the manifest: `manifest = migrated + skipped + quarantined + pending + failed + aborted`. Release gate additionally requires `pending = failed = 0` **and exactly one non-`ABORTED` process instance per `(runId, legacyId)`**, queried by variable.

   **The gate must wait for the exporter to drain before counting.** The variable query reads Camunda's secondary storage, which lags the engine by `flushInterval` (0.5s in the reference config, with a 1000-deep queue). A gate that counts immediately after the create loop sees fewer instances than exist, finds no duplicate, and **releases** — failing silently by passing, precisely when the batch is largest. The plan's own idempotency section already warns this query is eventually consistent; the gate must honour that warning.

   **Update (2026-09-17): a fixed drain sleep was not enough, and `migrate` proved it.** The lag bites the *liveness* check rather than the duplicate check — duplicates are found with SQL over the ledger, while `vanishedHeldCases` asks the engine. Run by hand the 3s sleep always sufficed, because a human takes seconds to type `reconcile` after `load`. Chaining the phases in one process removed that accidental margin: on a cold stack the gate asked before the export landed, read all three held instances as cancelled, and refused a release that was correct. It failed closed, which is the right direction and still the wrong answer. The check now polls each held instance until it is visible or `migration.visibility-timeout` (30s) expires, rather than sleeping a guess and believing the first reply. A genuinely cancelled instance costs the full timeout and then fails exactly as before.

   **Secondary storage:** Camunda uses `rdbms` secondary storage on the **same Postgres container as the ledger, in its own schema**. One database engine for the stack rather than two.
4. *(step 7)* Interrupted batch reruns without duplicating; the record surfaces as `CREATE_PENDING` and the gate refuses release until resolved.
5. Every released instance is returned by `/v2/user-tasks/search` filtered on its expected `elementId` + `candidateGroup`, **and** can be driven to a terminal state with stubbed workers without raising an incident.
6. Quarantine reason codes are separately counted, with **expected counts for the fixture run** so the criterion fails on a classification regression, not only on a reporting bug: `PREVALIDATION` = 3, `UNMATCHED` = 1, `OUT_OF_CUTOFF` = 1, `CONTRACT_UNSATISFIED` = 1, `CREATE_FAILED` = 0. Plus `AMBIGUOUS` from the overlap variant and the `REDUNDANT_RULE` warning count.
7. ~~Zero `notify-applicant` jobs activated between injection and release.~~ **REMOVED.** The POC BPMN has no service tasks, so nothing can fire and the assertion cannot fail. A test that cannot fail is not a test. See Accepted shortcuts.
8. Abort cancels every held instance and a subsequent run under a new `runId` reaches the gate. **"No citizen-visible effect" is defined, scoped to the aborted run's instance keys, as:** zero user tasks in a non-`CANCELED` terminal state, and no ledger row reaching `RELEASED`. (The notification clause is gone with criterion 7.)
9a. **(in POC)** The build-time check runs exhaustively over the 96-cell synthetic domain and reports the covered / uncovered / multi-hit partition, matching the table above exactly: 92 / 4 / 0.
9b. ~~Every field combination in the production profile hits exactly one rule.~~ **Removed from POC scope** — no production profile will be run. Carried to the programme. 9a over the synthetic domain is therefore the *only* exhaustiveness evidence this POC produces, and it proves the checker works, not that the rule set covers reality.
10. *(iteration 2, if run)* CSV and Adabas sources produce identical classification **canonically**: sort by `legacyId`, compare `{legacyId, outcome, targetElementId, reasonCode, ruleIds}` as a set. Row order, whitespace, timestamps and ISN formatting excluded.
11. **Volume:** 10,000 synthetic records complete a dry run and a held-creation run; throughput numbers are **reported, not thresholded**. This is the only criterion addressing "at scale"; it measures, it does not certify.
12. **Cleanup returns the model to normal.** After the `migrator` listener is removed and the model redeployed, a brand-new citizen application starts from the None Start Event and runs to a terminal state without halting. This closes the loop the docs warn about (*"Do not start new Camunda 8 process instances on models that still have the `migrator` execution listener"*) and is the difference between a migration that finishes and a service that never reopens.

## Why automatic positioning, and when it stops paying

There is a simpler option, and it must be written down so nobody thinks it was overlooked.

**The alternative: one reassessment queue.** Migrate every unfinished application into a single triage queue in the new system. A clerk opens each one, reads it, and sends it to the right desk. No inference, no decision table, no classification risk. It satisfies the hard cutover exactly as well — nothing stays in Adabas, no split brain — and it cannot silently misplace a case, because a human sees every one.

**Why we are not doing that.** It costs clerk time proportional to case count. At ~5,000 in-flight cases and roughly 4 minutes per case:

| Approach | Clerk effort | Roughly |
|---|---|---|
| Reassessment queue, all 5,000 by hand | ~333 hours | one person for ~8 weeks, or 8 people for a week |
| Automatic at 90% placement, 500 to triage | ~33 hours | one person for ~4 days |
| Automatic at 40% placement, 3,000 to triage | ~200 hours | one person for ~5 weeks |

**The break-even.** Automatic positioning earns its build cost when it can place confidently well above roughly **60-70%** of in-flight cases. Below that, clerks handle most of the work anyway and the machinery mostly adds risk and schedule.

**What this POC can and cannot tell you.** It proves the machinery works. It **cannot** tell you which row of that table you are in, because the placement rate is a property of the real Adabas data and production is out of POC scope. That number comes from the field-combination profile in "After the POC".

**The fallback, and it is a real one.** Quarantine already *is* a small reassessment queue. If the real placement rate lands low, the design degrades gracefully: more cases route to triage and the programme runs closer to the reassessment-queue model without rebuilding anything. That is a deliberate property, not a consolation.

**The placement rate is not fixed — it is driven down by iteration.** Once the POC is agreed and testing starts against real extracts, the dry run reports how many applications the rules could not place automatically. That number is the input to a loop, not a verdict:

```
   ┌────────────────────────────────────────────────────────┐
   │  dry run  ──►  unmatched count + the field combinations │
   │                that produced it                         │
   │      ▲                        │                         │
   │      │                        ▼                         │
   │  redeploy DMN  ◄──  investigate the causes with the      │
   │  (no code release)  business, add or amend rules where   │
   │                     it makes sense                       │
   └────────────────────────────────────────────────────────┘
        repeat until the unmatched count is small enough
        to accept — then, and only then, cut over
```

Three properties make this loop cheap, and they are why the design is shaped this way:

- **The dry run creates nothing.** `POST /v2/decision-definitions/evaluation` classifies the whole population without a single process instance, so the loop can run nightly against a fresh extract at no risk.
- **Rules live in a decision table, not in code.** Adding or amending a rule is a DMN redeploy that a business analyst can read and sign, not a software release.
- **Unmatched cases carry their evidence.** Each one records the exact field combination that matched nothing, so "investigate the causes" starts from a grouped list of real patterns rather than a hunt.

This also changes how the break-even should be read. The table above is a snapshot, not a prediction. The decision is not "is the rate above 60-70% today" but "can we get it there before the cutover date, and how many iterations does that take." **The first dry run against real data is therefore the most valuable single measurement in the programme** — it sets both the starting point and the slope.

Some residue always remains and should not be chased to zero: genuinely broken records, and combinations the business itself cannot interpret. Those are what quarantine is for.

### Why this problem exists at all

No commercial Adabas/Natural modernization vendor (Astadia, MOST, OneAdvanced, Semantic Designs, Digital Strategy Group) migrates in-flight process state. They convert **code and data model** and thereby keep process state implicit — `fee_paid` still means what it always meant, in Postgres instead of Adabas, so nothing needs inferring.

**The precise version, after challenge:** the vendors avoid inference by carrying the legacy *program* forward — the Natural code stays, so it keeps interpreting its own fields. Once that program is replaced, which this programme has already committed to, the fields have no interpreter and **someone must interpret them regardless** — into a BPMN token or a hand-written Java state machine. BPMN changes the form of the answer, not the existence of the question.

What is genuinely a choice is *how* you pay to place every case: automatic inference, or clerk hours through a reassessment queue (see "Why automatic positioning"). Inference is the cheaper way to pay above the 60-70% break-even. **That** is the purchase, and it is already reasoned about elsewhere in this doc.

Search also confirmed **no product migrates mainframe work items to a BPMN engine automatically.** The inference layer is genuinely build, not buy.

### Strangler and dual-run are different things, and only one is ruled out

Vendor and Camunda guidance favour parallel-run / strangler: *"a 'big bang' approach ... carries significant risk, high cost, and a high probability of failure."*

**What is ruled out:** running **one service** on both systems at once. That is the split-brain argument — a citizen's permit existing in two databases with divergent truth, where no clerk can say which is authoritative. It stands.

**What is NOT ruled out, and is in fact already the plan:** the **per-service strangler** — migrating one service at a time, each with its own hard cutover, while other services stay on Adabas. The multi-service seam accepted in this review *is* that pattern. It reduces blast radius and is fully compatible with everything here.

In-flight migration is mandatory under either, because each service's own cutover is still all-or-nothing.

**Brief the sponsor on the distinction, not on "we rejected the consensus."** Defending the wrong proposition is worse than not defending one. See OQ CEO-3.

### Permissions

Source is an **Adabas application file**: user ids plus dotted "conversation" strings, granted through groups.

```
  user_id  --> conversations[]      "12.4.7.3" = application . service . role . level
  groups   --> conversations[]      (grant by group, not per person)
```

**Task routing needs no per-case migrated data — but `candidateGroups` is not the enforcement point.** Both halves matter and an earlier draft of this section got the second half wrong.

True: `candidateGroups` is a **literal string in the BPMN** (`learner-permit.bpmn:179`), so a case landing on the right element carries the right group label without any migrated permission datum.

False, and corrected: that this makes permissions a solved group-to-group mapping. Verified in the reference implementation:

| Evidence | Finding |
|---|---|
| `TaskDto.java:9-12` | `candidateGroups` is **display-only** — *"no rule of this application is encoded in them"* |
| `SecurityConfig.java` | **zero** occurrences of `candidateGroup`; enforcement is `hasRole`/`hasAnyRole` over realm roles |
| `realm-export.json` | `groups` is **null**; `civil-servant` is a realm **role**; no user belongs to any group |
| `CaseAccessService.java:21` | *"Reviewers see everything"* — case visibility is all-or-nothing |
| `WorklistController.java:172-185` | back-office queue searches `UserTaskState.CREATED` with **no candidate-group filter** |

So the real mapping target is a **realm role**, not a group, and adding a back-office role requires coordinated edits in `Permissions.java` and `SecurityConfig.java` (documented at `CaseAccessService.java:49-52`). What genuinely holds is narrower: **one mapping per legacy group rather than per user.**

**Open dependency this creates:** decide whether the POC models `cashier` and `issuing-officer` as Keycloak **groups** or realm **roles**, and which layer enforces them. Unanswered, and it sizes the permission work.

**Starter identity does not dissolve, and it is load-bearing.** `assignee="=applicantId"` is an expression evaluated per case, matched against the Keycloak `preferred_username`. A legacy `user_id` mapping to no Keycloak subject means that person loses access to work they filed.

**POC assumptions:** permission data arrives as CSV; POC users are pre-seeded in Keycloak via an explicit demo setup task; no Keycloak realm construction.

**Camunda's identity migrator does not apply.** It migrates authorizations and tenants only, from a Camunda 7 database that does not exist here, and explicitly *"does not migrate Camunda 7 internally managed users, groups, and group memberships."* Camunda's stated alternative is integrating with an external IdP. Note also: **Camunda 8 supports GRANT only** — any restrict semantics have no direct target.

## Eng review corrections to fold in (2026-09-15)

Accepted findings not yet expanded inline. Each is a required change, not a suggestion.

**Correctness**

1. **Semantic equality must exclude provenance.** `ruleId` is an output column, so two redundant rules produce *different* output tuples and would be quarantined as `AMBIGUOUS` — the exact over-quarantining the distinct-output rule exists to prevent. Compare on `{outcome, targetElementId, reasonCode}` only; carry matched rule ids alongside, never inside, the comparison.
2. **Source-record identity must be separate from business identity.** Fixture 11b is "record missing `CASE_REF`", but `CASE_REF` *is* the ledger key — the fixture cannot be stored in the store meant to record it, and two records sharing a `CASE_REF` cannot both occupy a unique row. Add a source identity (`manifest line number + source hash`) that every rejected record can be counted under.
3. **The freeze must freeze interpretation, not just rows.** Row hashes omit the CSV header, so renaming a column changes classification while every row hash still matches. Bind the run to the source schema (header hash) and to the exact deployed DMN and BPMN versions, so a resumed run cannot mix interpretations.
4. **Normalisation must reject, not coerce.** "Never null" does not say what happens to a malformed boolean, an unrecognised vision result, or tied occurrence dates. Each is `QUARANTINE(PREVALIDATION)`. Truncation detection needs an independent occurrence count in the export; dynamically discovered columns alone cannot prove nothing was cut.

**Run lifecycle**

5. **Creation must be closed before counting.** Exporter drain does not stop *new* writes — a loader retry or a quarantine resolution can create an instance after the gate passes. The run needs an explicit `CREATION_CLOSED` transition; the gate counts against that frozen membership and release is authorised only for it.
6. **Abort must discover engine instances, not trust the ledger.** A create whose response was lost sits in `CREATE_PENDING`, outside the cancellation states, and a forced duplicate may have no ledger row at all. Abort queries the engine for every instance carrying this `runId` and confirms cancellation of each, whatever the ledger says.
7. **Partial release needs a recovery protocol.** Once any instance reaches `RELEASED`, batch abort is forbidden: recovery must finish releasing rather than cancel. State the cutover point explicitly and test crashes around the modification and the ledger commit.
8. **Reconciliation must check correspondence, not just arithmetic.** The identity proves bookkeeping. Additionally assert the expected engine set per process definition and ledger state, reject unexpected instances, and verify each instance has exactly the expected active task — not merely that *a* task matching the element and group exists.

**Performance**

9. Duplicate detection is **one aggregate query grouped by `legacyId`**, never one query per record.
10. The create loop is **batched with a bounded in-flight count**; the drain wait **polls for catch-up** rather than sleeping a fixed interval. Exporter `queueSize` is a real ceiling under bulk create.
11. Three ledger round-trips per record (intent, create, confirm) are **deliberate**. Do not batch them away — the intent write must be durable before the create or the crash-safety property is gone.

**Testing**

12. Framework: **Camunda Java client + `camunda-process-test-spring`** for engine assertions, **testcontainers-postgresql** for the ledger, JUnit for extract and classify units.

## Open Questions

1. **Unmatched rate on real data is unknown, and this POC will not reduce that.** The single largest programme risk, explicitly out of POC scope by decision. A green POC demo says nothing about it. See "After the POC".
2. **PE collapsing rule undecided.** Latest occurrence, first PASS, or attempt count? Blocks fixtures 2 and 7, and R8.

5. **Source freeze mechanics undefined against real Adabas.** The POC demonstrates the freeze *protocol* (manifest, hashes, gate). The mechanism that actually stops writes on the mainframe is unresolved and needs a named owner.
6. **Quarantine ownership unassigned** — including who decides `OUT_OF_CUTOFF` cases, which are live. **Owner required.**
6b. **OQ2 has no owner**, and unlike OQ5/6/8 it is on the critical path: it blocks fixtures 2 and 7 and R8. The POC proceeds on a provisional "latest occurrence" rule, but no production run may. **Owner required.**
6c. **Which UI serves triage** — Camunda Tasklist or the sibling POC's SPA. Decides the size of the Keycloak dependency. Needed before step 4.

## After the POC

The POC deliberately takes no dependency on production Adabas — not the data, not the model. That keeps it unblocked, and it bounds what the POC can claim.

**What a green POC proves:** the pipeline works. Extraction flattens group / MU / PE structures; classification places records or refuses to; the ledger survives interruption; held instances release, abort and reconcile; cleanup returns the model to normal service.

**What it does not prove, and must not be presented as proving:** anything about the real file. Not the rule count, not the unmatched rate, not extract throughput, not whether a durable business key exists. Those are untouched programme risks.

**The single highest-value action after the POC** is the one deferred here: a read-only aggregate count by field-combination over active records, returning counts per pattern and nothing else — no record contents, no citizen identifiable. It answers whether the rule set is eight rows or a hundred and forty, which is the difference between an engineering project and a rule-discovery project.

Adabas is not SQL, so the access path is the first sub-decision, and it belongs to the Adabas/Natural team:

| Path | Notes |
|---|---|
| Adabas SQL Gateway (CONNX) | A `GROUP BY` works directly; licensing status unknown |
| A Natural program | No new licence; accumulates counters in working storage |
| `ADASEL` / Adabas utilities | Selection and counting without application code |

Group by occurrence-independent expressions so the query does not wait on the collapsing rule decision: emptiness of `DATE_COMPLETED` / `ISSUED` / `EXPIRED`, `FEE_PAID`, count of vision-test occurrences (0/1/2/3+), whether any occurrence is `PASS`, the latest occurrence result, and emptiness of `USER_ID`. Answer the durable-business-key and case-age questions in the same pass.

This profile is the **first turn of the improvement loop** described under "Why automatic positioning". It sets the starting unmatched count; every dry run after it measures progress against that baseline.

## Worktree parallelization strategy

| Step | Modules touched | Depends on |
|---|---|---|
| Synthetic file model + fixtures + manifest + expected outcomes | `fixtures/` | — |
| BPMN + DMN + migrator listener | `processes/` | — |
| Probes M1-M8 | throwaway probe model | `processes/` |
| extract + classify | `migration-app/` | fixtures, processes |
| ledger + load | `migration-app/`, schema | extract/classify |
| reconcile + gate + release + abort | `migration-app/` | ledger + load |
| quarantine process | `processes/`, `migration-app/` | reconcile |

`Lane A: fixtures (independent)` / `Lane B: processes → probes (sequential)` / `Lane C: migration-app pipeline (sequential, shared module)`

**Execution:** launch A and B in parallel worktrees. B's probes gate everything in C. Then C runs sequentially — its steps all share `migration-app/`, so splitting them would only create merge conflicts.

**Conflict flag:** Lane B and the quarantine step both touch `processes/`. Sequence them.
